JUDGE THE PREMISE, NOT ONLY THE DIFF. A PR can be flawless line by line and still be the wrong change, so before the technical review, and with the same rigor, answer three questions for each PR. (2) WHAT DOES IT ASSUME: name the diagnosis and every assumption the approach rests on (what causes the problem, who calls this code, what the platform or a dependency guarantees, which case "cannot happen") and check each against the code yourself. The PR's own account of the cause is a claim to verify, never a fact to build on: trace the reported symptom down to where it originates. (3) IS THIS THE RIGHT FIX: does the change remove that cause, or only stop the symptom from showing? Suspect the second whenever the diff sits away from where the fault originates: a guard, a retry, a sleep or a longer timeout, a special case for the one reported input, a swallowed error, a test loosened until it passes, a cleanup after the fact. Ask what the same cause still breaks with this PR merged (another caller, the other platform, the next input of the same shape), and whether the repo already has a mechanism for this that the PR works around or duplicates.
